# Dev Log — 2026-09-19

## expense-summary: Directory-driven expense import

**Goal**: Replace typing every transaction into 随手记 and then hand-filling 32 categories a month with: drop six institutions' CSVs into a folder, run one command, get the month's categorised spending in `expense_records`.

### Delivered
- **Tool**: `tools/expense-import/` — Python 3.12, standard library only (`tomllib`), no backend or frontend changes.
  - `discover.py` — scans `~/finance-data/<YYYY-MM>/`, identifies each CSV by header, attributes transactions by their own date and **reports** how many fell outside the period.
  - `parsers/` — six institutions: Chase checking (pre-existing), Chase card, BOA checking, PayPal, Venmo, Robinhood card. Registry picks by header signature, tolerating preambles (`header_search_rows`).
  - `classify.py` + `rules.toml` — ordered rules, first match wins, every verdict carries its rule name. Load-time validation on regex, category id, `funding_target`.
  - `gates.py` — three fail-closed write gates, pure functions.
  - `reconcile.py` — diffs local aggregate against the remote period.
  - `apiclient.py` — the only module doing I/O, injected so the write path is testable end to end.
  - `write.py` / `run.py` — orchestration, escape-hatch flags, reporting.
- **159 tests.**

### Decisions
- **Thin, not a backend feature** — monthly, single user, rules change with each month's merchants. A rules file edited in place beats a rules-management UI.
- **Three gates, each for a failure that looks like success**: an unmatched merchant (visible in the data), a top-up whose platform statement is missing (visible only because checking recorded it), and a statement never exported at all (**visible nowhere** — the only gate that can catch it).
- **No catch-all rule.** Silently bucketing a new merchant into "uncategorised" is worse than refusing to write.
- **Currency isolation is the load-bearing invariant.** `expense_records` is keyed by (family, period, minor category, **currency**), so hand-entered CNY rows sit in the same period as ours and are structurally "remote with no local counterpart" — exactly what a diff deletes. Six dedicated tests; verified against real CNY rows the user entered through the app.
- **Venmo inbound nets against its category** rather than counting as income — this account is a reimbursement channel (you front a court booking or a group dinner, people pay you back), not a spending one.
- **Some things deliberately have no rule.** Large online Costco charges (a fridge, tyres and a bulk grocery run land in different categories at similar amounts, and the description carries no item detail) stay UNKNOWN so gate 1 asks each time.

### Process
- `/opsx:explore` → `propose` → `apply` → `archive`. TDD throughout.
- Five evaluator subagents: 96 / 96.8 / 97.6 / 99 / 95. Group 2 BLOCKed on a HIGH first pass — `check_funding_gaps` summed refund inflows into the gap total, so a platform refund could block a write over money that came back. Fixed with two regression tests, re-evaluated clean.
- Requirements and spec review each caught a real defect before any code: the idempotence hole (upsert never removes, so every corrected rule leaves its mistake behind) and the CNY deletion risk.

### Gotcha

Four payload bugs reached the first real write because a fake client accepts any payload — unit tests prove the code matches *the contract you believe in*, not that the contract is real:

1. `batch_save` omitted `expenseType`, which the backend requires and validates.
2. `familyId` was omitted on the reasoning that the controller overwrites it from the JWT. It does — but `@Valid` runs *before* the method body, and the field is `@NotNull`, so the request died at validation. Correct about the semantics, wrong about the order.
3. The client read `error` from failure bodies; the backend reports under `message`, so a wrong password printed the raw response dict.
4. The family endpoint is `/family`, not `/families` — assumed from the controller class name instead of reading its `@RequestMapping`.

And one design-level miss: **endpoint availability is not policy permission.** The reconcile design leaned on `DELETE /expenses/records/{id}`, verified the endpoint exists, and stopped there. `DataProtectionService` refuses every delete for a family with `is_protected` — assets, liabilities, income and expenses alike — and family 1 has it set. Rather than disable a standing safeguard over real financial history for a monthly convenience, the tool gave up deleting and now names every superseded row on each run until it is cleared in the app. That keeps the property reconciling existed for; only who removes it changed.

Separately, two CLI reporting changes appeared applied but were not, and both surfaced as an `AttributeError` *after* a real write had landed. The report is now its own function with tests that run it and read the output.

All five are recorded in CLAUDE.md.
